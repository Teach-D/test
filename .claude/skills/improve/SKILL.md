# Code Improver

기존 코드의 문제를 체계적으로 분석하고, 사용자 선택에 따라 개선한다.

## 워크플로우

```
분석 → 문제 정의 → 방안 제시 → 선택 → 수정 → 검증
```

## 1단계: 분석

대상 코드의 맥락을 먼저 파악한다.

- 이 코드의 역할이 무엇인가?
- 어디서 호출되고, 무엇에 의존하는가?
- 변경 시 영향 범위는?

분석 결과를 한 줄로 요약한다:

```
**맥락**: RouletteService.spin() — 룰렛 참여 처리, RouletteController에서 호출, PointService에 의존
```

## 2단계: 문제 정의

7가지 기준으로 코드를 평가한다. 문제가 없는 기준은 생략한다.

| 기준 | 확인 내용 |
|---|---|
| 가독성 | 이름, 구조, 흐름이 직관적인가? |
| 설계 원칙 | KISS, DRY, SRP 위반이 있는가? |
| 에러 처리 | 예외 상황이 적절히 처리되는가? |
| 성능 | N+1 쿼리, 불필요한 연산이 있는가? |
| 보안 | 입력 검증, 인젝션 위험이 있는가? |
| 테스트 용이성 | 의존성이 주입 가능하고 테스트하기 쉬운가? |
| 코드 중복 | 반복되는 로직이 있는가? |

출력 형식:

```
**코드 분석 결과**

| # | 기준 | 심각도 | 문제 |
|---|---|---|---|
| 1 | 설계 원칙 | 높음 | 하나의 함수에서 검증+조회+저장 모두 수행 (SRP 위반) |
| 2 | 에러 처리 | 중간 | 예산 초과 시 예외 없이 null 반환 |
| 3 | 가독성 | 낮음 | 변수명 d가 무엇인지 불명확 |
```

심각도 기준:
- **높음**: 버그, 보안 취약점, 심각한 설계 문제
- **중간**: 유지보수 어려움, 에러 처리 누락
- **낮음**: 네이밍, 코드 스타일, 사소한 중복

문제가 없으면 "분석 결과 개선이 필요한 항목이 없습니다"라고 안내하고 종료한다.

## 3단계: 방안 제시

문제별로 개선 방안을 제시한다. 심각도 높은 순서로 정렬한다.

각 방안에 포함할 내용:
- 변경 범위 (어떤 파일/함수가 영향받는가)
- Before/After 코드 예시
- 영향도 (동작 변경 여부)

출력 형식:

```
**개선 방안**

### 1. SRP 위반 해소 (높음)
- **변경 범위**: RouletteService.spin()을 3개 private 메서드로 분리
- **영향도**: 동작 변경 없음 (리팩토링)

**Before:**
fun spin(userId: Long) {
  // 검증 + 조회 + 저장이 한 함수에
}

**After:**
fun spin(userId: Long) {
  validateParticipation(userId)
  val point = calculatePoint()
  saveResult(userId, point)
}

### 2. 에러 처리 보강 (중간)
...
```

## 4단계: 선택

사용자에게 적용할 항목을 묻는다:

```
어떤 항목을 적용할까요?
- 전체 적용
- 번호로 선택 (예: 1, 3)
- 건너뛰기
```

## 5단계: 수정

선택된 항목을 코드에 반영한다.

규칙:
- coding 스킬의 규칙을 준수한다
- 한 번에 하나의 문제씩 수정한다
- 동작 변경 없이 구조만 개선하는 것이 기본 (리팩토링)
- 동작 변경이 필요한 경우 수정 전 사용자에게 반드시 고지한다
- 원본 코드의 의도를 훼손하지 않는다
- 수정 완료 후 커밋 규칙에 따라 git add + commit

## 6단계: 검증

수정 결과를 확인한다.

- 기존 테스트 실행 (있는 경우)
- 빌드 에러 확인
- 변경 전후 동작 동일성 확인

검증 실패 시 수정을 롤백하고 사용자에게 보고한다.
